# Simulation profile v2 boundaries

This is a partial independent emulator. It does **not** fully test every Bedrock add-on, recreate all graphics/menus/controls, or demonstrate 95% compatibility. Its built-in examples establish software conformance to the chosen model, not agreement with Minecraft.

## Runtime

The bounded world has a flat floor at y=0, coordinates within ±128, at most 2,048 blocks, 128 entities, 20,000 ticks, and 2,000 actions. Four MCP sessions may coexist. Sessions live in memory; export before closing. No world generation, dimensions other than the simulator overworld, fluids, redstone, networking, vanilla AI, full combat, persistence in LevelDB, resource-pack stacking, or platform-specific behavior is modeled.

Movement uses approximate speed/gravity and continuous axis-aligned sweeps. Thin barriers are checked without movement substeps. Selection rays intersect a separate boolean/cuboid selection box. It does not model sneaking over edges, swimming, step-up, climbing, flying, sprint timing, entity-to-entity collision or engine float rounding. Semantic `place`, `break`, and `interact` target explicit positions for tests; they do not enforce native reach or survival inventory consumption. Mining is immediate and respects only the boolean unbreakable setting; mining duration is not simulated.

Player inventories have 36 slots, maximum stack sizes, stack identity, names/lore, dynamic metadata, durability data, copy-returning reads, swaps and transfers. Entity containers require a supplied inventory component. This is not full NBT, equipment, enchantment, container rules, automatic durability wear, automatic dropped-item pickup, hunger or food behavior. Food is reported unsupported even though its component data is readable. Recipes support shaped/shapeless grids and roll back inputs on output overflow; tags, custom stations and ingredient data variants remain unsupported.

Entities support tags, filtered queries, typed property writes, health changes/hurt/death events, inventory and a limited filter language for component-group events. Effects are limited to speed, slowness, jump boost, regeneration and poison with approximate timing. There is no mob AI, armor, native attack/hurt cooldowns, death cleanup, resurrection lifecycle or complete damage rules. Commands and scoreboard objects share this world's state; command grammar, selectors and score identity objects are subsets, not native implementations.

## Scripts

QuickJS-NG executes JavaScript in a separate process. esbuild links virtual pack modules and lowers async functions so rejected promises can be tracked. Classes/private fields, destructuring, optional chaining, lexical scopes, generators, promises, async/await, top-level await and literal relative imports are exercised by tests. This does not establish complete ECMAScript or native Bedrock JavaScript conformance. Dynamic import expressions, external modules, eval/Function compilation and browser/Node APIs are unsupported. QuickJS's Intl/standard-library coverage can differ from Bedrock. Async transforms and promise observation change some reflective details; they are not a native rejection tracker.

The guest receives only a JSON bridge to modeled APIs, with no registered filesystem/network/Python-reflection functions. Node only compiles source in a virtual file system. Execution has a 3-second wall deadline per operation, a 64 MiB QuickJS heap, 512 KiB stack, 2,048 pending-job iterations and 4,096 API calls per exchange. Budget exhaustion fails the run; it does not prove the add-on would exceed native limits. This is not an independently audited hostile-code sandbox or an OS security boundary. There is no claim that these tests exclude vulnerabilities in the embedded engine/compiler.

Implemented API objects include subsets of world/system, dimensions, blocks/permutations, entities/player, ItemStack/Container, scoreboard and server-ui. Block handles read live state; vectors and many component data objects are snapshots. Custom hooks are onPlace, onPlayerInteract, onPlayerBreak, onTick, player onStepOn/onStepOff, and item onUse. Other hooks are explicitly reported. Timer delays are at least one simulated tick; jobs receive 64 yields per tick. Registration/world-load/player-spawn ordering, early execution and read-only restrictions are not fully reproduced. World calls at module initialization can succeed here even when a particular native API version prohibits them. Before-event cancellation is modeled for selected actions, but native callback timing is not guaranteed. API module versions in manifests do not select different API implementations.

Only implemented event names can be subscribed to without a blocker. Unrecognized imports/API calls are blocked or raise errors. Detection is incomplete: missing members may surface as ordinary script errors, and untouched branches cannot be verified by executing another path. A caught unsupported-operation exception still leaves a report finding. The model is one single-player overworld; no native networking, multiplayer scheduling, browser UI runtime or general command engine is present.

## Rendering and menus

CPU-rasterized textured cuboids, bone transforms, basic UVs, linear keyframes and limited animation controllers are previews. They do not implement native camera/render math, all texture orientation/version rules, native clipping, culling, translucency sorting, lighting, shaders, PBR, RTX/Vibrant Visuals, particles, sound, attachables or render-controller selection. Animation controller blend transitions and entry/exit side effects are unsupported. Some cube/UV mirroring details differ. The floor and interface are original simulator visuals.

The AI can operate inventory/pause screens and async ActionFormData, MessageFormData and ModalFormData. Forms include basic RawMessage text/translation, toggle/slider/dropdown/text inputs, headers/labels/dividers, pagination, submission and UserClosed/UserBusy responses. Rendered rectangles and click regions share one layout. Input values can also be supplied structurally. Layout, text clipping, dropdown cycling, slider clicks and pagination are original simulator behaviors. Tooltips, full translation/RawMessage semantics, form focus/accessibility, screen bindings, controller/touch layouts, custom JSON UI and Bedrock's actual screens are not implemented. Icons/dropped items are previewed from supplied textures; no vanilla assets are bundled. Missing textures produce a placeholder and an unresolved finding.

## Validation and results

The content scanner is not a full Bedrock schema implementation. Unknown top-level files/components are reported, but detection of unsupported nested fields is incomplete. A passed simulated assertion means exactly that; no native compatibility claim follows, even if the scanner found no gaps. Native performance, device compatibility and latest-build behavior are always unverified. `--target-version` records an intended target; it does not select a native engine.

Fixture setters and assertions can expose mistakes but cannot derive an author's intent. Auto-enumerating every block state does not establish that state behavior is correct. Images cannot decide whether a design is intended. A replay reproduces this model's result, not a native engine result. Image comparison uses a supplied reference and cannot validate all visual contexts.

A useful compatibility percentage would need an independent, representative, version-specific corpus with native observations or another justified oracle. No such corpus is included. We therefore publish no percentage; `accuracy_percent` is null, including in passing reports. Unsupported cases must remain in the denominator of any future benchmark.
