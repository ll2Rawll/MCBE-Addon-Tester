# Simulation profile v4 boundaries

This is a partial independent emulator. It does **not** fully test every Bedrock add-on, recreate all graphics/menus/controls, or demonstrate 95% compatibility. Its built-in examples establish software conformance to the chosen model, not agreement with Minecraft.

## Runtime

The bounded world has a flat floor at y=0, coordinates within ±128, at most 2,048 blocks, 128 entities, 20,000 ticks, and 2,000 actions. Four MCP sessions may coexist. Sessions live in memory; export before closing. No world generation, dimensions other than the simulator overworld, fluids, redstone, networking, vanilla AI, full combat, persistence in LevelDB, resource-pack stacking, or platform-specific behavior is modeled.

Movement uses approximate speed/gravity and continuous axis-aligned sweeps. Thin barriers are checked without movement substeps. Selection rays intersect a separate boolean/cuboid selection box. It does not model sneaking over edges, swimming, step-up, climbing, flying, sprint timing, entity-to-entity collision or engine float rounding. Semantic `place`, `break`, and `interact` target explicit positions for tests; they do not enforce native reach or survival inventory consumption. Mining is immediate and respects only the boolean unbreakable setting; mining duration is not simulated.

Player inventories have 36 slots, maximum stack sizes, stack identity, names/lore, dynamic metadata, durability data, copy-returning reads, swaps and transfers. Entity containers require a supplied inventory component. This is not full NBT, equipment, enchantment, container rules, automatic durability wear, automatic dropped-item pickup, hunger or food behavior. Food is reported unsupported even though its component data is readable. Recipes support shaped/shapeless grids and roll back inputs on output overflow; tags, custom stations and ingredient data variants remain unsupported.

ItemStack construction/assignment validates counts and clamps to the declared stack maximum. Name/lore setters enforce modeled limits and restricted-phase rules; RawMessage lore is blocked. Clones copy metadata independently, item-use events carry the selected stack's metadata, and dynamic-property writes require a non-stackable item type. Full native item metadata validation, serialization, byte limits and component privileges remain incomplete.

Entities support tags, filtered queries, typed property writes, health changes/hurt/death events, inventory and a limited filter language for component-group events. Effects are limited to speed, slowness, jump boost, regeneration and poison with approximate timing. There is no mob AI, armor, native attack/hurt cooldowns, death cleanup, resurrection lifecycle or complete damage rules. Commands and scoreboard objects share this world's state; command grammar, selectors and score identity objects are subsets, not native implementations.

## Scripts

QuickJS-NG executes JavaScript in a separate process. esbuild links virtual pack modules and lowers async functions so rejected promises can be tracked. Classes/private fields, destructuring, optional chaining, lexical scopes, generators, promises, async/await, top-level await and literal relative imports are exercised by tests. This does not establish complete ECMAScript or native Bedrock JavaScript conformance. Dynamic import expressions, external modules, eval/Function compilation and browser/Node APIs are unsupported. QuickJS's Intl/standard-library coverage can differ from Bedrock. Async transforms and promise observation change some reflective details; they are not a native rejection tracker.

The guest receives only a JSON bridge to modeled APIs, with no registered filesystem/network/Python-reflection functions. Node only compiles source in a virtual file system. Execution has a 3-second wall deadline per operation, a 64 MiB QuickJS heap, 512 KiB stack, 2,048 pending-job iterations and 4,096 API calls per exchange. Budget exhaustion fails the run; it does not prove the add-on would exceed native limits. This is not an independently audited hostile-code sandbox or an OS security boundary. There is no claim that these tests exclude vulnerabilities in the embedded engine/compiler.

Implemented API objects include subsets of world/system, dimensions, blocks/permutations, entities/player, ItemStack/Container, scoreboard and server-ui. Block handles read live state; vectors and many component data objects are snapshots. Custom hooks are onPlace, onPlayerInteract, onPlayerBreak, onTick, player onStepOn/onStepOff, and item onUse. Other hooks are explicitly reported. Timer delays are at least one simulated tick; jobs receive 64 yields per tick. `waitTicks` accepts positive integer delays. Imports of modeled modules must be declared in their owning pack's manifest.

The profile models Script API v2 early execution, startup registration, then worldLoad/playerSpawn. Modeled bridge calls reject premature world access and writes during before-events; reads and documented messaging are permitted. Promise continuations drain after the restricted callback returns, so a cancellation after `await` is too late. Registration expires after startup. This is not a complete per-method/version privilege matrix: pure guest object operations, native error classes, exact tick/microtask ordering and version-specific exceptions can differ. Other @minecraft/server major versions are reported unsupported. Minor/patch versions do not select different API implementations.

Only implemented event names can be subscribed to without a blocker. Unrecognized imports/API calls are blocked or raise errors. Detection is incomplete: missing members may surface as ordinary script errors, and untouched branches cannot be verified by executing another path. A caught unsupported-operation exception still leaves a report finding. The model is one single-player overworld; no native networking, multiplayer scheduling, browser UI runtime or general command engine is present.

## Rendering and menus

CPU-rasterized textured cuboids, bone transforms, basic UVs, linear keyframes and limited animation controllers are previews. Perspective triangles are clipped to the near plane. Entity yaw and explicit render controllers select resources through aliases, arrays and Molang expressions. Ordered bone material/visibility rules and RGB tint are modeled. Each layer requires one texture and `entity` or `entity_alphatest` material; shader variants, multi-texture materials and intermediate alpha tint are blocked. They do not implement native camera/render math, all texture orientation/version rules, culling, translucency sorting, lighting, PBR, RTX/Vibrant Visuals, particles, sound or attachables. Some cube/UV mirroring details differ. The floor and interface are original simulator visuals.

Animation clocks start on activation and restart on state re-entry. Ordered transitions run at most once per controller per simulated tick. Initialization, pre-animation, on_entry/on_exit Molang, finished-state queries, stop/loop/hold behavior for timed clips, and position/rotation cross-fades are modeled. Interrupted cross-fades, cross-fades involving scale, remap curves, custom anim_time_update, start/loop delays, effects and Catmull–Rom interpolation remain unsupported. Constant clips without a duration are maintained while active. Animations use the 20 Hz simulation clock; native render-frame interpolation and precise multi-controller composition are unverified.

Molang supports arithmetic, conditions, scopes, bounded loops/break/continue, return, variable structs, null coalescing, resource arrays and selected numeric functions/queries. Numeric domain errors evaluate to zero and produce content findings when evaluated in a world. Unknown features are not converted to zero. Molang random/die-roll and easing functions, actor-reference operators, for_each and many world queries remain unsupported. Python arithmetic is not a native float32 implementation; precision, overflow and edge-case parity are unverified.

The AI can operate inventory/pause screens and async ActionFormData, MessageFormData and ModalFormData. Forms include basic RawMessage text/translation, toggle/slider/dropdown/text inputs, headers/labels/dividers, pagination, submission and UserClosed/UserBusy responses. Rendered rectangles and click regions share one layout. Input values can also be supplied structurally. Layout, text clipping, dropdown cycling, slider clicks and pagination are original simulator behaviors. Tooltips, full translation/RawMessage semantics, form focus/accessibility, native screen bindings, controller/touch layouts and Bedrock's actual screens are not implemented. Icons/dropped items are previewed from supplied textures; no vanilla assets are bundled. Missing textures produce a placeholder and an unresolved finding.

## Function and command boundaries

Functions execute supplied text without a shell. A root call shares a 10,000-command ceiling and depth limit of 32; execute expansion is capped at 128 contexts. Other world/event budgets may stop execution earlier. Ordinary command failures are retained as errors while later function lines continue. Unsupported commands stop that execution and remain findings. The scanner checks function roots and execute clauses, including uncalled functions, but does not validate every unused leaf argument form.

`tick.json` executes listed functions on each advanced simulation tick. It starts after the model's script world-load phase. Native functions can run before world loading finishes; that phase and exact ordering relative to native scripts are not reproduced. Selectors cover a bounded single-player subset, with seeded random selection. Native random sequences, selector tie-breaking, coordinate float precision, command success counts and whole-number position centering are unverified. Absolute coordinates currently use their literal numeric value; use explicit decimals for precise fixture positions. Blocks still use floored positions. Other dimensions, command blocks, permissions, selector player-level/rotation/item filters, and complete command grammar are unsupported. See [COMMANDS.md](COMMANDS.md).

## JSON UI boundaries

The independent interpreter loads supplied `_ui_defs.json`, `_global_variables.json` and named templates. It models selected control types, inheritance, scoped variables, explicit global/view bindings, typed expressions, fixed/parent-percentage sizes, anchors, stack layout, clipping and layer order. Buttons, toggles and text entry share their layout with PNG rendering and clickable regions. Keyboard tab/directional links, pressed mappings and pointer hover/press/release are modeled. Text is rendered with Pillow fonts; metrics and antialiasing are not native.

`ui_open` and `ui_bind` provide fixture screens/data. They do not prove that Bedrock would open the screen, supply the binding or handle the emitted button ID. Native templates are not fabricated; absent references and bindings block the result. Native JSON UI factories, collections, hardcoded renderers, modifications/pack merging, content/sibling/fill sizing, animation, sound, full focus/input capture, touch/controller layouts, and native handlers remain gaps. Template array overrides replace arrays; native per-field merge behavior and lexical namespace edge cases are not fully calibrated. Input timing, alpha/clip inheritance, pixel rounding and all default values need independent native references.

UI expansion is limited to 512 live nodes, depth 32, 512 named definitions and a 4,096-control static audit. Expressions have an 8 KiB/2,048-operation budget. Logical viewports are 160–1920 by 120–1080; individual control extents are at most 4,096 and coordinates ±16,384. There are at most 256 fixture bindings/variables at open and 256 emitted UI events. Input/texture/unsupported-field failures remain findings. See [JSON-UI.md](JSON-UI.md).

## Validation and results

The content scanner is not a full Bedrock schema implementation. It audits selected component subfields, all animation/controller states, render-controller fields and Molang query/function references, including unexecuted branches. Detection remains incomplete. Reported `coverage` counts detected field occurrences, not behavior coverage; `detection_complete` stays false. A passed simulated assertion means exactly that; no native compatibility claim follows, even if the scanner found no gaps. Native performance, device compatibility and latest-build behavior are always unverified. `--target-version` records an intended target; it does not select a native engine.

Fixture setters and assertions can expose mistakes but cannot derive an author's intent. Auto-enumerating every block state does not establish that state behavior is correct. Images cannot decide whether a design is intended. A replay reproduces this model's result, not a native engine result. Image comparison uses a supplied reference and cannot validate all visual contexts.

A useful compatibility percentage would need an independent, representative, version-specific corpus with native observations or another justified oracle. No such corpus is included. The bundled 58-case [conformance suite](CONFORMANCE.md) uses original expectations derived from published contracts and retains its three known gaps. Its contract pass rate applies only to those selected cases; it is not a native accuracy rate or a sample of all add-ons. `accuracy_percent` stays null, including in passing reports. User-supplied suites retain unverified provenance and cannot set a native accuracy score. Unsupported cases remain in the denominator.
