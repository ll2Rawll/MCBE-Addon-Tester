# Independent Bedrock simulation research

Research checked 2026-11-11. The product requirement is a simulator with no game runtime and no AI API. This document distinguishes published specifications, third-party implementations, implemented behavior, and unmeasured fidelity. Earlier real-client research is preserved in [LEGACY-RESEARCH.md](LEGACY-RESEARCH.md); that workflow is not the active design.

## Proposed route to broader fidelity

The architecture is an independent, executable model of the add-on surface: pack loader → feature inventory → virtual state and script interpreter → animation/renderer → input/menu model → assertions and evidence. The host AI selects scenarios, inspects output and interprets the report. Deterministic traces allow the same inputs to be rechecked after a model improvement.

This makes simulation without Minecraft possible for implemented features. It does **not** make native compatibility automatic. The public content specifications omit some engine behavior; implementing one subsystem does not establish all its interactions. A simulator can reproduce its own mistake consistently.

A credible path toward high measured coverage requires versioned feature contracts, independently sourced reference observations, adversarial add-ons, held-out tests, and per-subsystem mismatch reports. Reference datasets can be consumed without installing the game on an end user's machine. This project does not yet include a native reference corpus or a measured compatibility percentage. No empirical basis for “95% of all add-ons” was found in this research.

Version 0.3 replaces the handwritten ES2017 interpreter with an embedded JavaScript engine and adds forms, slot containers, commands, scoreboards, entity APIs and more precise box intersections. Further increments still needed include native JSON UI/bindings, full render-controller evaluation, complete API semantics/privileges, world mechanics and independent calibration.

Regression work reproduced a false-pass bug caused by unobserved rejected module/async promises. The revised worker checks promise failures after draining jobs and tests both caught and uncaught rejection paths. Subsequent revisions added atomic inventory/block validation, invalidated removed-entity containers, and stopped accepting subscriptions to events the model never emits. These are correctness improvements to the simulator; they do not quantify native parity.

## Version handling

The earlier metadata check on 2026-11-11 returned stable BDS `1.26.63.1` and preview `1.26.70.24` from [Minecraft's official download metadata](https://net-secondary.web.minecraft-services.net/api/v1.0/download/links). That is a server-build observation, not proof of the Windows client's version or simulator support. Marketing, binary, content-format, and Script API version numbers are distinct.

The simulator currently has one named profile, `independent-bedrock-subset-v2`. `target_version` records the user's intended build. It does not select engine binaries, claim latest-version parity, or update component semantics automatically. The profile changes because execution, state representation and collision results differ from v0.2; old evidence retains its original profile label.

## Verification performed

The original workshop scenario exercises ten expectations; the v0.3 emulator scenario adds eleven expectations around forms, cancellation, entities, inventory metadata and scoreboards. Both produce PNGs, assertions and replay evidence without game files. The test suite includes a real MCP client exercising async form submission and image output. CI runs the suite, both scenarios, replay, lint and wheel checks on Windows and Linux. The earlier v0.2 workshop fixture also passed Mojang Creator Tools 0.21.0 static validation with zero errors, zero warnings and four format-version recommendations; that observation does not validate new scripting semantics. These are simulator/software checks. Native gameplay, GPU fidelity and complete UI compatibility were not verified.
